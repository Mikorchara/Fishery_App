## 后续目标（建议顺序）

1. **固定一套组员可复现的比赛版。** 记录电脑端提交、板端代码或发包版本、板端启动方式、FFmpeg 版本和协议样例。用一台队员电脑从全新下载的源码跑一次模拟入口，再用同一局域网跑一次设备联调。验收时记录电脑的接收地址和板端流地址如何确定、两次以上连续的新检测窗口、RTSP 画面、一个网页事件以及一条经授权的 QQ 回答。保留必要截图和脱敏样例，运行库、凭据和个人身份留在本机。
2. **把事件验收到可复核。** 由硬件组确认行为结果 ID、采集时间、覆盖字段及正常窗口是否上报，管理端记录各样例的预期事件和实测结果。至少覆盖同一 E1 持续更新、同一行为文件重复携带、新版本触发一次 E2、断报触发 E3 并由下一份及时报告结束。再决定 E1 的恢复规则，三个完整无信号窗口的设想须以每窗都有明确检测覆盖为前提。
3. **做一个小范围真实养殖试点。** 建议先选一个池、一种水质指标和一个视频源，核对设备时间、人工对照和数据缺失，再决定要不要扩大。预计连续运行前，制定报告及监测库的容量、保留期限与备份策略，明确断网重连、重发和恢复后新鲜度的验收方法。若要开放外网或增加多人使用，再单独设计身份认证、角色权限和通知管理。

11 月 13 日联调曾遇到板端高负载、系统 FFmpeg 和 RTSP 超时。临时暂停高占用进程后，系统 FFmpeg 能返回版本，板端 RTSP 也成功读到一帧。进程来源和重启后是否复发尚未确认。建议用比赛版复现时由板端负责人一并核对开机负载、视频出帧和报告时间。

本阶段优先做复现和验收。新增事件种类、更换模型、扩建知识库可以等试点明确需求后再排期。具体排期和负责人由团队确定。

## 11 月 16 日补充的改进方向

### Agent 回复与可靠性

- **先定回复样式。** 从 Web 和 QQ 各挑几条常见问题，保留匿名原答并写一版理想答复。当前事件可以先用一句话给结论，有事件时列出事件和状态，末行合并观测时间与来源。QQ 由模型生成正文，程序再附实际来源，修改时要一起检查是否重复。
- **单独检查查询失败。** 先读共享的 Agent 指令，再沿着「模型选择工具 → 参数校验 → 读取事件 → 生成回答」走一条真实案例。回归应覆盖同义问法、有事件、查询成功但无匹配、数据缺失或过期、参数不合法和未调用工具。用运行详情或错误码判断停在哪一步，再决定调整回答指令、查询入口还是工具调用。

学习顺序可按请求流程、提示词与回复展示、故障定位。在仓库里可从 [Agent 开发指南](deep-dive/AI_BACKEND_DEVELOPMENT_GUIDE.md)开始，再看[当前事件工具的装配](../apps/ai_service/active_event_execution.py)和 [QQ 来源说明的生成](../apps/ai_service/channel_agent_presentation.py)。

### QQ 多人事件通知

- **现状。** 自动通知只有一个已验证的私聊接收人。新配对会替换原绑定，并关闭自动通知。群聊提问成员名单与自动通知接收人分别配置。
- **拟议目标。** 设置页支持逐人配对、列出和移除接收人。已有单人配置保留为名单中的第一位，新增人员各自完成私聊验证。启动时显示人数及身份摘要，由操作者确认本次发送范围。
- **验收。** 同一事件分别通知各接收人，每人每次事件转换只提交一次。分别记录平台确认、失败及送达未知，验证其中一人发送失败时其余人仍可收到，以及重启和移除接收人之后的行为。先用虚构接收人离线测试，再由操作者实际验收 QQ 平台的投递。
