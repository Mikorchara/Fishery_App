## 11 月 16 日补充的改进方向

### Agent 回复与可靠性

- **先定回复样式。** 从 Web 和 QQ 各挑几条常见问题，保留匿名原答并写一版理想答复。当前事件可以先用一句话给结论，有事件时列出事件和状态，末行合并观测时间与来源。QQ 由模型生成正文，程序再附实际来源，修改时要一起检查是否重复。
- **单独检查查询失败。** 先读共享的 Agent 指令，再沿着「模型选择工具 → 参数校验 → 读取事件 → 生成回答」走一条真实案例。回归应覆盖同义问法、有事件、查询成功但无匹配、数据缺失或过期、参数不合法和未调用工具。用运行详情或错误码判断停在哪一步，再决定调整回答指令、查询入口还是工具调用。

学习顺序可按请求流程、提示词与回复展示、故障定位。在仓库里可从 [Agent 开发指南](deep-dive/AI_BACKEND_DEVELOPMENT_GUIDE.md)开始，再看[当前事件工具的装配](../apps/ai_service/active_event_execution.py)和 [QQ 来源说明的生成](../apps/ai_service/channel_agent_presentation.py)。

### QQ 多人事件通知

- **已实现。** 设置页支持逐人配对、列出和移除最多 4 位接收人。原有单人绑定仍可使用，新增人员各自完成私聊验证。群聊提问成员和私聊通知接收人分别配置。启动时显示人数及身份摘要，由操作者确认本次发送范围。
- **验收。** 同一事件分别通知各接收人，每人每次事件转换只提交一次。分别记录平台确认、失败及送达未知，并覆盖单人投递失败、重启与移除。用虚构接收人离线测试，真实 QQ 客户端的投递由操作者验收。见[设置步骤](deep-dive/QQ_BOT.md#首次在网页绑定事件接收人)。

## 延后验收（2026 年 11 月 17 日）

以下两项保留为现场待办，恢复时间由团队决定。本轮先研究 Agent 架构和提示词。

- [ ] **开发板视频联调。** 用当前网络地址启动板端和电脑接收器，通过板端视频入口确认网页播放 RTSP 画面，同时核对新检测窗口和设备事件是否更新。记录两端的版本、验证时间和异常情况。
