# 设备怎么把数据发给 Management

**现在支持两条独立的数据通道。** 开发板报告可以接收并在网页查看；真实水质传感器和实时视频仍需单独对接。日常接收脚本已改为**局域网免令牌**，开发板不必填写`X-Device-Token`。

| 数据 | 发送到哪里 | 网页用途 |
|---|---|---|
| 原 Simulator 的水质/视觉统计 | 本机 `8766/api/ingestion/batches` | Monitoring、水质历史、规则事件和已授权 AI 查询 |
| 开发板 TEXT_PACKAGE_API v1 检测报告 | 独立接收器 `8780/api/fish/reports` | 保存原报文、视频页展示，并由Web同步为设备异常事件 |
| 根目录 `sample.mp4` | 启动时通过 `-DemoVideo` 指定 | 仅本地录像播放，与上述两路数据独立 |

开发板报文目前**没有水温、pH、溶解氧**。设备联调时，这三项仍由 Simulator 模拟并标注 SIMULATOR。设备报告不参与 AI 水质查询，也不会把设备加入水质设备选择框。

新版报告的事件来源标为 **DEVICE REPORT**：

| 事件 | 如何判定 |
| --- | --- |
| 外观异常待核查 | 新鲜完整窗口有明确外观异常标签和目标数。同一设备持续异常更新一条事件；外观观测缺失时转为待核实。 |
| 行为模型异常待核查 | 新的行为文件版本有视频被模型标为异常。同一版本只记一次；旧行为随新检测窗口重复携带，不会刷新行为时间。 |
| 设备报告更新中断 | 先连续收到 3 个按时的有效窗口，再约 3 分钟未收到新窗口时记录一次。下一份按时的新鲜完整窗口结束这次中断。 |

报告恢复更新只代表数据恢复上报。当前协议不能证明各外观类别都完成了检测，外观和行为事件不会因缺包或缺失字段自动标记为已恢复。旧格式继续使用原有事件规则。

## 1. 先准备电脑

电脑和开发板连接同一可信局域网。在 **Management 根目录**打开 PowerShell，先完成根目录 [开始使用](../../开始使用.md) 的环境安装和 `outputs/qq-m3-real-test` 初始化。

另建报告存储（只执行一次，不覆盖已有文件）：

```powershell
.\scripts\dev\Start-DeviceReports.ps1 -InitStore
```

看到 `DEVICE_REPORT_STORE_CREATED` 即完成。默认文件是 `outputs/device-reports/device-reports.sqlite3`，与原 Monitoring 库分开。如果提示已存在，跳过初始化，不删除重建。

仅检查参数（不打开数据库、不读令牌、不联网）：

```powershell
.\scripts\dev\Start-DeviceReports.ps1 -Check
```

## 2. 启动网页，只模拟水质

先正常关闭旧 Web / Simulator，再执行：

```powershell
.\scripts\dev\启动演示系统.cmd
```

先在**运行模式菜单选`2`设备联调**，再在Simulator中选水质场景，推荐`1`正常。四个普通启动脚本都会自动绑定本项目`outputs/device-reports`和设备`fish-monitor-orin-01`，不需要再复制长命令。此模式不会生成模拟视觉；“疑似疾病、摄食减少”等视觉参数不生效，水质异常规则仍正常运行。选`1`完整模拟则保持原行为，不绑定设备报告。

要同时播放录像，改用`.\scripts\dev\启动视频演示系统.cmd`，同样先选运行模式`2`。打开 http://127.0.0.1:8766 的“视频监控”：左侧模拟水质、中央录像、右侧设备报告。

`fish-monitor-orin-01` 必须与开发板`device_id`一致。若组员使用其他ID或需要自定义报告目录，使用显式入口，并同步修改下一步接收器的`-DeviceId`/`-Directory`：

```powershell
.\scripts\dev\run_local.ps1 -DataRoot "$PWD\outputs\qq-m3-real-test" -ShowTerminals -InteractiveScenario -OpenBrowser -SimulationMode water-only -DeviceReportDirectory "$PWD\outputs\device-reports" -DeviceReportDeviceId <开发板实际ID>
```

普通脚本不会自动创建报告库或启动8780接收器；首次先完成第1步初始化。没有收到设备报告时，不会用模拟视觉填充设备结果。

## 3. 单独启动报文接收器

另开 PowerShell，进入同一项目。用 `ipconfig` 找到电脑当前局域网 IPv4（换网络后可能变化），将下面占位符替换为实际地址：

```powershell
.\scripts\dev\Start-DeviceReports.ps1 -Serve -Bind '<电脑局域网IPv4>' -DeviceId fish-monitor-orin-01
```


这条命令直接启动，**不再要求输入令牌**。看到 `DEVICE_REPORT_LISTENING` 且 `auth_mode` 为 `NONE_LAN`，保持这个窗口运行。

- 默认端口8780；Web仍是8766，互不占用。
- 不填 `-Bind` 时只监听127.0.0.1，开发板访问不到。
- 只绑定具体的私网IPv4，不使用0.0.0.0。防火墙如需放行，仅限可信专用网络、开发板地址与此端口；程序不自动改防火墙。
- 首版是局域网 HTTP，不含 TLS，不要直接暴露到公网。

旧令牌方式仍兼容：确实需要时在命令末尾加`-RequireToken`，电脑端按提示输入双方私下约定的32～128位字母数字，开发板才需要发送同一`X-Device-Token`。它不是QQ或Qwen密钥，不从开放平台领取。普通联调无需启用此选项。

## 4. 组员在开发板上填写

```http
POST http://<电脑局域网IPv4>:8780/api/fish/reports
Content-Type: application/json
```

默认**不用填令牌，也不用加其他认证请求头**。接收器仍只接收绑定设备ID的报告，报文格式、大小、重复ID和频率处理保持原规则。

正文按原 [TEXT_PACKAGE_API.md](development/TEXT_PACKAGE_API.md) 的 v1 JSON 发送。保留 `schema_version`、`report_id`、`device_id`、`sent_at`、`window`、`has_abnormality`、`report_text`、`detection`、`abnormalities`、`behavior`、`measurement`。本端不要求添加水质字段。

- 时间带时区，使用实际采集时间，电脑与开发板先校时；不得发送未来时间。
- 同一报文重传保留 ID 和内容；新报文换 ID。同 ID 不同内容会拒绝。
- `measurement` 尚无结果时用 `null`。行为任务未出结果时用 `null` 或明确的未知状态对象。
- JSON最大16 KiB，窗口最长1小时，最多60次请求/分钟。建议正常和异常窗口都上报；仅异常上报时，沉默不能证明恢复。
- 原文示例的窗口起止和 `duration_s` 可能不一致，实际发送应校正；接收器保留原证据并返回警告，不替设备改时间。

返回 `accepted` 表示已提交到独立报告库；`duplicate` 表示相同报文已保存。403先检查设备ID及是否误带浏览器`Origin`；仅启用`-RequireToken`时才检查令牌。409检查重复ID内容，413检查大小，429降低频率，503检查存储状态。不要遇错就无限重试。

## 5. 验收和停止

1. 发一条真实报告，检查开发板收到 `accepted`。
2. 报告收齐并通过校验后，在视频页核对设备、检测窗口、外观和行为。体长、模型指标和原始包在「查看报告记录」中查看；收包进度在「传输检查」中核对。
3. 相同报文重传应返回 `duplicate`，页面不增加重复记录。
4. 超过120秒的观测标为过期；这是报告时效，不是设备在线或疾病恢复判定。
5. 接收器窗口按 Ctrl+C 停止；Web/Simulator按原方式停止，存储保留。

### 网页里的结果怎么读

右侧显示报告时效、鱼群峰值、外观异常和行为摘要。行为按其结果文件版本标注时间；同一个版本随新包携带时会标明。点「查看报告记录」可在宽屏弹窗选一份完整报告，查看检测、体长、行为和折叠的传输证据。展开「传输检查」可查看未收齐或校验异常的报告及原始分包。

| 项目 | 可以说明什么 | 不能说明什么 |
|---|---|---|
| 检测 | 新版显示峰值帧可见目标数、峰值异常帧的标签与目标数；旧版继续显示其原有口径 | 不是鱼池存量，也不是疾病确诊 |
| 体长 | 每个测量目标的像素长度、设备给出的估计长度及质量提示 | 未标定的毫米估计不能当作真实体长；缺失不补成0 |
| 行为 | 旧报告提供片段及异常标记；`peak_frame_v1` 提供各视频的模型结论 | 新检测窗口可能附带旧行为文件版本，行为结果只能按自身来源和时间解释 |

同一时间下出现的 4 个分包可以属于一份报告。网页按分包编号与摘要核对、合并展示。接收库保留原始分包，传输检查中可查看缺包和校验失败的提示及原始文本。

检测窗口、体长采集和行为片段的时间可能不同，请分别核对；合并只解决展示，不证明这些任务逐帧对应。`video_replay` 表示录像回放推理，不是实时摄像头。网页中央的`sample.mp4`仍只是独立的本地播放素材。

## QQ设备事件提醒（已有QQ配置的电脑）

先保持上面的接收器运行，再用普通QQ启动脚本，在**运行模式菜单选择`2`**。它会使用上面的同一份报告目录和设备ID，无需新增JSON配置；Web约每2秒同步一次。Bot沿用已有私聊接收人，在原启动审批中一并显示设备报告披露范围。

```powershell
.\scripts\dev\启动QQ演示系统.cmd
```

要播放`sample.mp4`，改用`.\scripts\dev\启动QQ视频演示系统.cmd`并选`2`，不要同时启动两个入口。非默认ID或报告目录使用`Start-ManagementStack.ps1`的显式绑定参数。尚未绑定成功验证的QQ接收人时，只记录/展示事件，不擅自选择QQ用户或群。新版外观异常沿用原设备视觉异常的私聊提醒，仍需批准相同的设备和接收人；行为异常和报告中断只在网页展示。Simulator 通知规则不变，设备通知不调用Qwen、不占AI轮数。

通知人工验收：收到一份带外观异常的新鲜报告 → 接收器返回 `accepted` → 网页出现“外观异常待核查”（旧格式为“设备视觉异常报告”）→ 已批准的 QQ 私聊收到 `DEVICE REPORT` 提醒。不要修改旧包时间冒充新观测。重发同一报文应返回 `duplicate`，不增加事件或通知；等待过期后应显示“状态待核实”。

原始库继续独立保存；Monitoring仍为v2，不增加表或迁移。处理进度与设备事件同事务保存，重启会续处理已收报文；不要删除或重建报告库来清空进度。报告同步失败不停止Simulator，视频页显示事件同步暂不可用。设备接收器和Web必须同时运行；Bot只读事件，不承担入库。

页面合并展示最近的报告，原始分包继续留存；独立库上限5000条原始报文，满后明确拒绝新报文，不自动删除历史。达到上限请停接收后由维护者备份并安排新存储，不清空旧库。

录像回放推理的连续自动上报、分包合并和事件更新已现场验证。实时摄像头视频流及实际检测准确性需分别验收。

原模拟批次的精确格式见 [监测协议](development/INTEGRATION.md)；四个日常入口见 [启动说明](BUILD_RUN.md)。
